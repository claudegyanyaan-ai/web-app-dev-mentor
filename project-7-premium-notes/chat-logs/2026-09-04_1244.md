# Project 7: Premium Notes (Subscription Billing) - Chat Log

## Starting point
Project 7 (forked from Project 5's auth-enabled Tasks & Notes PWA) had already been scaffolded
with a Todoist-style freemium model — a free plan capped at 5 total tasks + notes, and a
₹149/month "Premium" subscription that removes the cap — wired up against Razorpay
Subscriptions in test mode. Picking the project back up, the immediate goal was simply to get
a real end-to-end test subscription payment working in Razorpay's sandbox, which turned out to
be the wrong problem to solve.

## Razorpay sandbox: ruled out, not fixed
Net Banking and plain UPI were checked against Razorpay's own docs first, since a working
alternative to cards would have been the easy fix — neither is actually supported for
Subscriptions in test mode, only cards are. Stripe was floated as an alternative and briefly
pursued (the user was fine switching to USD pricing to make it possible), but Stripe's own
support docs confirm new India-based account signups are entirely blocked and invite-only, so
Stripe was ruled out for this project's location.

Rather than keep debugging Razorpay on the existing account, the decision was made to isolate
whether the problem was account-specific: a brand-new Razorpay test account, a brand-new plan
(`plan_TXp91XETumh3Kl`), and a fresh subscription were created from scratch. The exact same
generic "We are facing some trouble completing your request" failure reproduced identically —
same test card, same flow, completely fresh account and keys — this time triggered directly
from Razorpay's own dashboard checkout UI, not even through our code. That reproduction was the
conclusive signal: this was a Razorpay-side sandbox/platform issue, not anything fixable on our
end, and continuing to debug it further would have been wasted effort. Decision: switch payment
gateways.

## Switching to Cashfree
Cashfree was chosen as the replacement — a mainstream Indian gateway with proper Subscriptions
support. Signup ran into its own snag: the standard flow drops straight into a full KYC wizard
(business PAN, beneficial owner details, document upload) before granting any dashboard access,
contradicting Cashfree's own docs about test-mode not requiring KYC. Found a workaround: a
"Try Test Environment" button on Cashfree's product listing page (under the Subscriptions card)
skips the KYC wizard entirely and drops straight into the sandbox dashboard.

From there: created a plan (`plan_1788496415032_me7yw8`, ₹149/month), generated test API keys,
and proved out a full subscription authorization end-to-end directly from Cashfree's own
dashboard — eNACH/e-Mandate via the "Bank Account" tab, landing on a built-in
"Simulator - E_MANDATE" page with one-click Simulate Success/Failure buttons. This is a genuine
sandbox testing capability Razorpay's own dashboard didn't offer, and it's what let the gateway
choice be validated before touching any code. A webhook was then configured
(`/billing/webhook` on the Render backend) for six subscription events — after first getting
created under the wrong tab ("Payment Gateway" instead of "Subscriptions") and having to be
deleted and recreated in the right place.

## Code migration: Razorpay to Cashfree
With the gateway proven out manually, the actual codebase migration was done directly (with
explicit go-ahead from the user) rather than talked through step by step:

- **`backend/requirements.txt`**: `razorpay` swapped for `requests` (Cashfree has no official
  Python SDK for this API; plain HTTP calls are used instead).
- **`backend/main.py`**: the Razorpay client init replaced with a `cashfree_headers()` helper
  (`x-client-id` / `x-client-secret` / `x-api-version`); `/billing/create-subscription` rewritten
  to POST to `https://sandbox.cashfree.com/pg/subscriptions` with a self-generated
  `subscription_id` (Cashfree requires the caller to supply one) and return the
  `subscription_session_id` the frontend needs for checkout; `/billing/webhook` rewritten for
  Cashfree's HMAC-SHA256 signature scheme (`timestamp + raw body`, signed with the **Client
  Secret** — unlike Razorpay, Cashfree has no separate webhook-specific secret).
- **`backend/schemas.py`**: `SubscriptionCreateOut` trimmed to just `subscription_session_id`.
- **`backend/models.py`**: deliberately left untouched — the existing
  `razorpay_subscription_id` column is reused to store Cashfree's subscription ID instead of
  being renamed, since `Base.metadata.create_all()` only creates missing tables and won't add
  or rename columns on an existing one; renaming would have meant a real migration for no
  functional benefit.
- **`frontend/app/layout.js`**: the Razorpay checkout script swapped for
  `https://sdk.cashfree.com/js/v3/cashfree.js`.
- **`frontend/app/page.js`**: `handleUpgrade()` rewritten to call the Cashfree SDK instead of
  opening a Razorpay modal.

## Local testing: three real bugs found and fixed
Testing the new flow locally (`uvicorn` + `npm run dev`) surfaced three genuine, unrelated
bugs, each debugged from first principles rather than guessed at:

**Bug 1 — wrong SDK method entirely.** The first attempt called
`cashfree.checkout({ subscriptionSessionId: ... })`, which is the *payments* checkout call, not
the *subscriptions* one — Cashfree's checkout page rejected it outright
(`payment_session_id is not present or is invalid`), confirmed via the Network tab that the
backend really was returning a valid session ID. After that fix (correcting the parameter key)
the button still visibly did nothing at all, with clean console output. Fetching Cashfree's own
docs directly settled it: subscriptions checkout is a **separate SDK method**,
`cashfree.subscriptionsCheckout({ subsSessionId, redirectTarget })` — not `checkout()` with a
different key. The wrong method silently no-ops instead of throwing, which is why it looked like
nothing was happening.

**Bug 2 — the PWA service worker fighting local dev.** Before that fix was even found, the
Network tab showed something odd: every JS chunk *and* the Cashfree SDK script itself were being
intercepted by `sw.js` (cache-first, inherited from Project 5's PWA setup), showing up as `304`s
routed through the service worker instead of the network. This is exactly the kind of thing that
can serve a stale cached bundle indefinitely in dev, and matched a Chrome console warning about
a "cross-world service worker resource mismatch" on the Cashfree script. Root cause: a
cache-first service worker has no business running during `npm run dev` at all — it's meant for
the production PWA. Fixed by making `RegisterSW.js` register the worker only in production, and
in development actively unregister any existing registration and clear its cache instead.

**Bug 3 — Cashfree's redirect back is a POST, not a GET.** After checkout genuinely started
working, the mandate authorization ("Simulate Success" on Cashfree's sandbox simulator)
completed fine, but the redirect back to the app's `CASHFREE_RETURN_URL` failed with an
HTTP 405. Cashfree posts the callback back to the return URL rather than using a GET redirect —
a plain Next.js page only accepts GET. Fixed by adding a small dedicated route,
`frontend/app/billing/return/route.js`, that accepts both GET and POST and forwards the browser
into a normal GET page load, then repointing `CASHFREE_RETURN_URL` at that route.

## Deployment: three more real bugs, all in production only
Once the code was pushed and Render/Vercel env vars updated for Cashfree, going live surfaced a
fresh set of issues that never showed up locally:

**Bug 4 — `SECRET_KEY` accidentally deleted from Render.** After swapping the four Razorpay env
vars for the four Cashfree ones, login started failing for every account with a generic
"Incorrect email or password" — while signup worked fine. Diagnosed methodically rather than
trusting that message at face value: signup for an email that should have been brand-new still
said "already registered" (proving the database was intact and unchanged), and checking the
Network tab's actual status code showed a real **500**, not a genuine 401. The one thing
`/login` does that `/signup` doesn't is sign a JWT via `SECRET_KEY` — checking Render's
Environment tab confirmed it had been deleted by accident while the Razorpay vars were being
removed. Restored from the local `.env` value and redeployed; login worked immediately after.

**Bug 5 — webhook silently matching nothing.** Even with checkout genuinely completing (a
subscription visibly reaching "Active" status in Cashfree's own dashboard) and every webhook
delivery logging a clean 200 response, the app never flipped a user to Premium. The webhook
handler's code was checking `payload["data"]["subscription"]["subscription_id"]` — a structure
guessed at rather than verified. Pulling the actual delivered payload from Cashfree's Webhook
Logs (Payload tab) showed the real shape: `subscription_id` lives directly under `data`, and
again under `data.subscription_details.subscription_id` — there's no `data.subscription` object
at all. Separately, the logic for *when* to grant Premium ("AUTH" substring-matched against the
event type name) was also wrong in principle, since a `SUBSCRIPTION_AUTH_STATUS` event can
legitimately still be `BANK_APPROVAL_PENDING`, not a finished authorization. Rewrote the handler
to read the real field paths and to key the Premium flip specifically off
`subscription_status == "ACTIVE"`.

**Bug 6 — the fix that "didn't work" because it was never actually deployed.** After fixing and
pushing bug 5's code, the exact same symptom persisted on a fresh test account. Checking
Render's Events tab (rather than assuming the push alone was enough) showed the *previous*
commit was still the latest live deploy, with its trigger listed as "Manually deployed by you
via Dashboard" — a strong signal auto-deploy-on-push isn't enabled for this service. A manual
"Deploy latest commit" picked up the real fix.

## Verified working, end to end
With all three deployment bugs fixed, a fresh signup → Upgrade to Premium → Bank Account
checkout → Simulate Success → redirect-back round trip on the real production URLs
(`web-app-dev-mentor-uwgt.vercel.app` / `premium-notes-backend.onrender.com`) finally completed
correctly: the subscription reached Active status in Cashfree, the webhook fired and matched the
right user, and the app itself showed Premium status with the 5-item cap lifted — confirmed with
multiple separate test accounts. A few accounts tested in quick succession briefly sat at "Bank
Approval Pending" before settling to Active a short while later, which is expected sandbox
processing delay rather than a bug — the webhook correctly leaves `plan` on "free" until the
real Active status comes through, then flips it on its own without any extra checkout attempt.

## Status as of this log
Subscription billing is fully working end to end in production on Cashfree, including the
freemium cap, checkout, mandate authorization, and webhook-driven plan upgrade. Remaining for
close-out: a final pass over the webhook's failure-path event handling
