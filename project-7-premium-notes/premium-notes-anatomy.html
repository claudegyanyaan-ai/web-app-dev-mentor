Project 7 of 10 · Anatomy

Premium Notes (Subscription Billing)

Project 5's auth-enabled Tasks & Notes PWA, extended with a Todoist-style freemium model — a 5-item free cap and a ₹149/month Premium plan — backed by real recurring-payment subscription billing. Built first against Razorpay, then rebuilt against Cashfree after conclusively proving Razorpay's sandbox itself was broken, not this project's code.

Next.js PWA→ FastAPI + JWT→ Postgres · Vercel+Render+Neon+Cashfree

Overview

Project 7's job was to add real billing to an existing app rather than build billing as its own toy demo — the free/paid split had to actually gate a feature (item count) that the rest of the app already had, and the payment had to be a genuine recurring subscription with a webhook-driven upgrade, not a one-off "mark as paid" button.

Scope: fork Project 5's Tasks & Notes PWA, cap the free plan at 5 items total (tasks + notes combined), and add a ₹149/month Premium subscription that lifts the cap once payment is authorized. What wasn't in scope going in — but became the actual story of this project — was discovering mid-build that the first payment gateway chosen was itself broken in its own sandbox, and having to swap gateways without losing any of the freemium logic already built.

A fourth party sits alongside the usual three tiers: Cashfree. The frontend talks to it directly for hosted checkout (via its JS SDK), the backend talks to it directly to create subscriptions (REST API), and Cashfree talks back to the backend on its own initiative via webhook whenever a subscription's status changes — the one part of this architecture where an external service pushes data in, rather than the app pulling it.

Why the payment gateway was swapped

The project started on Razorpay. Its sandbox checkout consistently failed with a generic "We are facing some trouble completing your request" error — reproduced identically on a completely fresh Razorpay test account, a fresh plan, and fresh API keys, triggered straight from Razorpay's own dashboard checkout UI rather than this project's code. That reproduction is what turned "a bug to fix" into "a platform issue to work around": if a brand-new account with nothing this project touched still fails the exact same way, the problem isn't here.

Stripe was considered as an alternative next, but Stripe's own support docs confirm new India-based account signups are invite-only and blocked entirely — ruled out immediately for this project's location. Cashfree was chosen instead, and — critically — proved out manually through its own dashboard (a full eNACH mandate authorization, using a built-in "Simulate Success" sandbox simulator) before a single line of this project's code was touched, so the gateway choice itself was validated independently of the migration.

Key concepts

Access control

Server-side freemium gating

The 5-item cap is enforced on every write in the backend — never trusted from the frontend alone.

Debugging

Isolating a platform bug

Reproducing a failure on a brand-new, untouched account is what proves it isn't your code.

SDK

checkout() vs. subscriptionsCheckout()

Payments and subscriptions are genuinely different SDK calls — the wrong one fails silently.

Security

Raw-body webhook signatures

HMAC verification needs the unparsed request body — re-serialized JSON breaks the signature.

Reliability

Status, not event name

An event firing doesn't mean the state it implies is final — read the actual status field.

Ops

Push ≠ deploy

Auto-deploy can be silently off — the hosting dashboard's live commit is the source of truth.

Bugs, debugged for real

Every one of these was an actual failure hit mid-build, not a scripted lesson.

Razorpay sandbox — platform issue, not a bug to fix

Generic checkout failure reproduced identically on a completely fresh account, plan, and keys, straight from Razorpay's own dashboard. Ruled out as fixable here; the gateway was swapped instead.

Wrong Cashfree SDK method

cashfree.checkout({ subscriptionSessionId }) was used — the payments call, not cashfree.subscriptionsCheckout({ subsSessionId }), the subscriptions-specific one. Failed on Cashfree's own page with an invalid-session error, then silently no-op'd after a partial fix.

Service worker intercepting the Cashfree SDK script in dev

The cache-first PWA service worker (correct for production) was intercepting fetches for the Cashfree SDK and the app's own JS bundles during npm run dev, matching a browser console warning about a "cross-world service worker resource mismatch." Fixed by registering it production-only and unregistering/clearing it in development.

405 on the payment gateway's return redirect

Cashfree posts back to return_url with an HTTP POST; a plain Next.js page only accepts GET. Fixed with a dedicated route.js accepting both methods and forwarding to a normal page load.

SECRET_KEY deleted from Render by accident

Lost while swapping the four Razorpay env vars for Cashfree's. Broke every login (JWT signing) while leaving signup unaffected — diagnosed by checking the real HTTP status (500, not a genuine 401) rather than trusting the frontend's generic "Incorrect email or password" text.

Webhook handler reading the wrong JSON path

Assumed data.subscription.subscription_id; the real payload nests it under data.subscription_details.subscription_id. 200 responses the whole time — it was silently matching nothing. Found by reading an actual delivered payload from Cashfree's Webhook Logs.

A fix that was committed and pushed, but never actually deployed

Render's auto-deploy-on-push was off for this service — the corrected commit sat live-but-unbuilt on GitHub, with the Events tab still showing the previous commit as the running deploy, until a manual "Deploy latest commit" was triggered.
