Build checklist

  • Forked from Project 5's auth-enabled Tasks & Notes PWA
  • Todoist-style freemium gating — 5-item cap (tasks + notes combined) enforced server-side on every write
  • ₹149/month Premium plan, INR pricing throughout
  • Payment gateway swapped mid-project from Razorpay to Cashfree, after conclusively reproducing a Razorpay sandbox platform bug on a completely fresh account (Stripe considered and ruled out — new India signups are invite-only)
  • Cashfree Subscriptions API: self-generated subscription_id, plan creation, subscription_session_id checkout flow
  • Cashfree JS SDK v3 (subscriptionsCheckout, not the plain payments checkout call)
  • Webhook endpoint with HMAC-SHA256 signature verification (timestamp + raw body, signed with the Client Secret)
  • Plan upgrade driven entirely by the webhook's real subscription_status ("ACTIVE"), not by event-type name matching
  • Existing razorpay_subscription_id DB column deliberately reused (not renamed) to store the Cashfree subscription ID, avoiding a schema migration
  • Deployed as two services — backend to Render, frontend to Vercel — verified live end-to-end with multiple real test accounts

Bug fixed — wrong Cashfree SDK method: cashfree.checkout() (payments) was used for a subscription session instead of cashfree.subscriptionsCheckout() — silently did nothing instead of erroring.
Bug fixed — service worker intercepting the Cashfree script in dev: the cache-first PWA service worker (fine in production) was serving stale/mismatched responses for the Cashfree SDK during npm run dev. Fixed by registering it production-only, and actively unregistering/clearing it in development.
Bug fixed — 405 on the payment gateway's return redirect: Cashfree redirects back to return_url with a POST, not a GET; a plain Next.js page only accepts GET. Added a small route that accepts both and forwards into a normal page load.
Bug fixed — SECRET_KEY deleted from Render by accident: lost while swapping Razorpay env vars for Cashfree ones — broke every login (JWT signing) while leaving signup unaffected. Diagnosed by checking the real HTTP status code (500, not a genuine 401) rather than trusting the frontend's generic error text.
Bug fixed — webhook reading the wrong JSON path: the handler assumed data.subscription.subscription_id; the real payload nests it under data.subscription_details.subscription_id. Found by pulling an actual delivered payload from Cashfree's Webhook Logs rather than guessing from docs.
Bug fixed — a pushed fix that was never actually deployed: Render's auto-deploy-on-push was off for this service; the corrected commit sat live-but-unbuilt on GitHub until a manual "Deploy latest commit" was triggered.

Concepts introduced

Full plain-English explanations in CONCEPTS.md. Summary:

  • Server-side freemium gating — never trust a client-side item-count check
  • What a subscription mandate actually authorizes, vs. a one-time payment
  • Recognizing a platform bug (vs. your own code) by reproducing it in isolation
  • Cashfree's create-subscription → subscription_session_id → hosted checkout flow
  • Payments checkout vs. subscriptions checkout as genuinely separate SDK calls
  • Webhook signature verification over the raw request body, not re-serialized JSON
  • Never trust a webhook payload's shape without reading a real delivered one
  • An event firing isn't the same as the state it implies being final
  • git push ≠ deployed — auto-deploy can be off with no obvious signal
  • Reusing an existing DB column across a provider swap to avoid a schema migration

Checkpoint quiz

1. Why was the free-plan item cap enforced in the backend instead of just hiding the "Add" button on the frontend once 5 items are reached?
2. What made the Razorpay failure a "platform bug, not our bug," rather than something to keep debugging?
3. Why did calling the Cashfree SDK's checkout() method with a subscription session ID fail silently instead of throwing a clear error?
4. Why does webhook signature verification need the raw, unparsed request body instead of the parsed-then-reserialized JSON?
5. Why was a subscription_status of "ACTIVE" used to grant Premium, instead of just reacting to any event whose name contains "AUTH"?
6. A code fix was committed and pushed to GitHub, but the bug persisted identically afterward — what turned out to be true, and how was it confirmed?
