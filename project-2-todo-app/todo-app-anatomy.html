Project anatomy · recap

To-Do App Anatomy

Project 1 was a page that sat still and looked nice. Project 2 is a page that remembers things — every click changes what's stored, and what's stored decides what's drawn. This doc walks through how that loop actually works.

01 Data flow — click to pixel

In Project 1, HTML was basically the whole story: content sat in the file, CSS painted it. Here there's a loop running underneath the page, and it's worth seeing as one path:

1 · ActionUser clicks / types / submitsAdd task, tick a box, hit Delete
→
2 · HandlerJS event listener firesOne delegated listener catches it
→
3 · StateThe tasks array changespush, splice, or flip a property
→
4 · SavelocalStorage updatedJSON.stringify(tasks)
→
5 · RenderList redrawn on screenwipe + rebuild from the array

Nothing on screen is ever edited directly. Every visible change happens because the array changed first, and the render step read the array again. That indirection — never touch the pixels, always touch the data and re-draw — is the single most important habit this project was building toward Project 3's framework.

02 What "state" actually means

State is just: the data your app is holding right now, while the tab is open. Here it's nothing more exotic than a JS array sitting in memory:

let tasks = [ { text: "Buy milk", done: false, editing: false }, { text: "Walk the dog", done: true, editing: false } ];

Everything you see — the strikethrough on "Walk the dog," the checkbox being ticked, the Edit box appearing — is just this array being read and turned into HTML. Change the array, and the next render shows the change. This is exactly the mental model React formalizes in Project 3; here we're doing it by hand so the concept is visible, not hidden behind a library.

03 Page vs. app

Both projects are "just HTML/CSS/JS in a browser" under the hood — there's no hard technical line. But there's a real difference in what the page is for:

Project 1 — static page
  • Content is fixed in the HTML file
  • JS only toggles a CSS class (menu open/closed)
  • Reload always shows the same thing
  • No data is created, changed, or remembered
Project 2 — interactive app
  • Content is generated from data (the tasks array)
  • JS creates, edits, and deletes that data
  • Reload shows whatever YOU left it as
  • The page has memory (localStorage) — it's stateful

04 Key aspects this project covered

JS·01

Event delegation

One click listener on the list handles every button, forever — even ones that don't exist yet.

JS·02

Render-by-rebuild

Wipe the list, redraw it from the array. Simple to reason about; the precursor to what React automates.

JS·03

data-* attributes

Tags each button with which task index it belongs to, so the delegated handler knows what was clicked.

JS·04

Template literals

Backtick strings with ${...} build the HTML for each row directly from the data.

DATA

localStorage + JSON

Browser storage only holds strings, so data is stringified going in and parsed coming back out.

DBG

DevTools console

Used to catch the exact error and line number that led to diagnosing the prompt() issue.

05 The prompt() bug — not every red error is your fault

The first "Edit" button called window.prompt() — a native browser popup. It threw Uncaught Error: prompt() is not supported.

Root cause

The page was being previewed inside an embedded VS Code webview (visible from the file:/// URL), which disables native dialogs like prompt()/alert()/confirm() for security. This wasn't a mistake in the code — it was a limitation of that specific preview environment.

Fix: instead of asking the browser for a popup, we built the edit UI ourselves — an editing flag on each task object that makes renderTasks() show an inline input + Save button instead of the normal row. More code, but it works everywhere, not just in browsers that allow native dialogs.

06 Deployment — a second, independent project

Project 2 lives in the same combined GitHub repo as Project 1, but was deployed as its own separate Vercel project — same account, same repo, different Root Directory (project-2-todo-app). Each project gets its own URL, its own build, and redeploys independently: pushing to project-1-portfolio/ never rebuilds Project 2, and vice versa. That's what makes one combined repo workable for a whole 10-project ladder instead of ten separate repos.
