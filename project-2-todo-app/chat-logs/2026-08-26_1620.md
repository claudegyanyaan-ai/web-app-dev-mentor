Date: 2026-08-26 (Asia/Kolkata)

## Kickoff
Explained why this project matters conceptually: Project 1 was static (page never changed
after load); this one introduces **state** — data that changes over time and that the UI
must stay in sync with — the foundational idea behind every real app going forward.
Introduced localStorage as the simplest form of persistence (no server/database yet).
File structure mirrored Project 1's shape deliberately, so scaffolding needed no new
explanation. Day budget: 2–3 days per instructions doc.

## Build sequence
1. **Folder + index.html skeleton** — form with `#task-input`/`#task-form`, empty
   `<ul id="task-list">` container. Explained the shift from Project 1: HTML now provides
   an empty container: JS decides what renders inside it.
2. **Core add/render logic** — `tasks` array as single source of truth; `renderTasks()`
   pattern (wipe + rebuild from state) introduced explicitly as "the simplest way to
   guarantee the screen matches the data" and flagged as the exact problem React (Project 3)
   solves properly. `event.preventDefault()` on form submit explained (stops page reload).
   Verified working: typed task rendered as a bullet.
3. **Edit/delete/complete-toggle** — introduced **event delegation** (one listener on the
   parent `<ul>`, not one per button, because renderTasks() destroys/rebuilds all `<li>`s
   every time) and `data-index` attributes to map a clicked element back to its array
   position. First version used `prompt()` for editing.
   - **Bug:** `prompt()` threw `Uncaught Error: prompt() is not supported` in the browser
     context being used (an embedded VS Code preview/webview, which commonly disables
     native dialogs). Diagnosed via DevTools console.
   - **Fix:** rewrote editing as inline UI — an `editing: true/false` flag per task drives
     `renderTasks()` to swap between the normal view and an `<input>` + Save button, no
     browser dialog involved. Framed as a UI-state concept, same "state drives rendering"
     idea applied to a new kind of state (editing status vs. task data).
4. **localStorage persistence** — `saveTasks()` (`JSON.stringify` into `localStorage`) and
   `loadTasks()` (`JSON.parse` back out) added; `saveTasks()` called after every real data
   mutation (add/toggle/delete/save-edit) but deliberately NOT after just entering edit mode
   (a UI-only state flip, not a data change worth persisting). `loadTasks()` runs before the
   first `renderTasks()` on page load. Verified: tasks survived a full page refresh.
5. **Styling pass** — card layout, teal accent (`accent-color` on checkboxes), strikethrough
   via a descendant selector (`li.done .task-text`) explained explicitly, mobile media query
   with `flex-wrap` for the button row. Verified visually — all working as intended.
