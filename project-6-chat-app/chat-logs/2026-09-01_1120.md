and reports back) scaffold project-6-chat-app/backend: venv, pip install (fastapi, uvicorn,
sqlalchemy, psycopg2-binary, python-dotenv, python-jose, bcrypt, pydantic, email-validator,
python-multipart), requirements.txt, database.py (SQLAlchemy engine/session, identical pattern

provides, it's a locally generated random value used only for signing JWTs), and .gitignore.

Built models.py (User, PasswordResetToken -- Conversation/ConversationParticipant/Message
deliberately deferred to the next step to keep this one focused on auth), schemas.py, auth.py
(copied verbatim from Project 5's hash_password/verify_password/create_access_token/

POST /signup, POST /login (OAuth2PasswordRequestForm-based), POST /forgot-password (generates

directly in the response body since there's no email service), POST /reset-password (validates

## Conversations + messages REST layer (continued)

Built Conversation, ConversationParticipant, and Message models (a join-table pattern --
first time this pattern's been needed, since 1:1 and group chats are both just conversations
with N participants). Added POST /conversations, GET /conversations, POST
/conversations/{id}/messages, GET /conversations/{id}/messages, all protected and
membership-checked. Explained to the user why some responses need manual serialization
(schemas.ConversationOut assembled by hand via a serialize_conversation() helper) rather than
plain Pydantic from_attributes, since participants live in a separate join table.

Verified end-to-end in Swagger: created a second test user (testuser2), created a 1:1
conversation between testuser1 and testuser2, posted and listed messages successfully.

Bug/gap found by the user: POST /conversations created a brand-new conversation every time
instead of reusing an existing 1:1 thread between the same two people. Fixed by adding a
dedup check (a join + group-by-count-distinct query) that looks for an existing non-group
conversation containing exactly both users before creating a new one. Verified: calling
POST /conversations twice for the same pair now returns the same conversation id both times.

## WebSocket live messaging

Added a WebSocket endpoint (/ws/conversations/{id}) so messages appear instantly for other
participants without polling. Introduced an in-memory ConnectionManager (conversation_id ->
list of active sockets) and a get_user_from_token() helper, since the JWT has to be passed as
a query param (?token=...) rather than an Authorization header -- browsers can't attach
custom headers to a WebSocket handshake. Noted for the user that this in-memory approach only
works with a single backend server process, which is fine for now but worth revisiting if the
app is ever scaled to multiple instances.

Bug hit and fixed: the endpoint originally called websocket.close() with a custom code before
calling accept() when auth/membership checks failed -- Starlette/uvicorn can't deliver a real
close-reason code before the handshake is accepted, so the browser just saw a generic
abnormal-closure 1006 with no useful information. Fixed by accepting first, then closing with
4001 (bad token) or 4003 (not a participant) if the checks fail.

Bug hit and fixed: first WebSocket connection attempt 404'd with "No supported WebSocket
library detected" in the uvicorn logs -- plain `uvicorn` doesn't bundle WebSocket support.
Fixed with `pip install websockets` and a requirements.txt refresh.

Built a small standalone ws_test.html page (not part of the app) to test WebSockets directly,
since Swagger's /docs can't exercise them -- lets two browser tabs each hold a JWT and connect
to the same conversation. Verified real live delivery: a message typed in one tab appeared
instantly in the other tab (and vice versa) with no refresh.

Bug hit and fixed: an instruction to "update the <script> block" in ws_test.html was
ambiguous and the user replaced the entire file with just the <script> tag, losing the page's
HTML structure (blank page, no visible inputs). Fixed by resupplying the complete file.

## Presence (online/offline)

Added last_seen (nullable DateTime) to the User model. First schema change to an *existing*
table rather than a new one -- explained to the user that Base.metadata.create_all() only
creates missing tables, it won't add a missing column to a table that already exists, so a
manual `ALTER TABLE users ADD COLUMN last_seen TIMESTAMP;` was run directly in Neon's SQL
Editor before restarting the server (acceptable since it's still test data, not a real
migration tool situation yet).

Added a separate global /ws/presence WebSocket endpoint (connected once per app session, not
per-conversation) plus a PresenceManager tracking which user_ids are currently connected.
On connect/disconnect it broadcasts a presence event only to "contacts" -- other users who
share at least one conversation with this user -- rather than to everyone globally. On
disconnect, last_seen is stamped. Also added GET /conversations/{id}/presence as a plain REST
fallback for a client's initial page load, before its WebSocket connects.

Extended ws_test.html to open both the conversation socket and the presence socket together
on Connect, logging presence events inline with chat messages for easy testing.

Verified end-to-end with two tabs: connecting testuser2 in tab 2 correctly logged
"testuser2 is ONLINE" in tab 1; closing tab 2 correctly logged "testuser2 is OFFLINE" in
tab 1 shortly after.
