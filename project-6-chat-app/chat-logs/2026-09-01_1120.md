# Project 6: Real-Time Chat App - Chat Log

## Kickoff and scope (carried over from earlier in the day)
Project 5 (auth-enabled tasks + notes PWA) was closed out, and Project 6 was scoped through
back-and-forth as a WhatsApp/Telegram-style real-time chat app: both 1-to-1 and small-group
rooms, full JWT auth reused from Project 5's pattern, a password-reset flow (in-app displayed
reset token/link, since there's no email service in this stack), online/offline presence, and
image/file sharing. Typing indicators and read receipts were explicitly deferred out of scope.
The app must work on web, Windows, Mac, and Android via the same PWA approach used in
Project 5.

Build order agreed: core auth + password-reset + conversations + live messaging first
(milestone 1.0), then presence, then image sharing, then PWA packaging, then deployment, then
close-out docs. Folder settled on project-6-chat-app/ (renamed from an initial
project-6-realtime-chat/). Step 1 (backend auth + password-reset endpoints) was scaffolded
once already earlier the same day.

## Repo problem found and fixed
Picking Project 6 back up on Praveen's Mac (device praveens-macbook-air-local), the repo copy
at ~/Praveen/web-app-dev-mentor turned out to have been obtained via GitHub's "Download ZIP"
button rather than `git clone` -- confirmed by the folder having no .git history at all, and by
the ZIP-vs-clone folder-naming difference (GitHub names ZIP extracts <repo>-<branch>, e.g.
web-app-dev-mentor-main, which is why the user saw that name and had renamed it back to
web-app-dev-mentor by hand).

project-6-chat-app existed locally but was completely empty. Checking GitHub confirmed it was
empty there too -- the earlier same-day Step 1 scaffolding had never actually been pushed, so
nothing was lost by starting over, it just needed to be rebuilt.

User asked to "start fresh here." Converted the ZIP-downloaded folder into a proper git clone
in place: `git init`, added the origin remote, fetched, then `git checkout -f -B main
origin/main` plus `git clean -fdx` to align the working tree exactly with GitHub. This required
device_request_delete_permission (the device bridge blocks deletes by default) since git needed
to overwrite/remove existing files and its own lock files during the checkout. Result: Praveen's
Mac now has a real git-tracked clone of web-app-dev-mentor, in sync with origin/main, with
Projects 1-5 intact and project-6-chat-app confirmed empty/untracked (matching GitHub).

## Step 1 backend rebuilt: auth + password-reset
Had the user (via VS Code terminal, hand-holding style -- one step at a time, user executes
and reports back) scaffold project-6-chat-app/backend: venv, pip install (fastapi, uvicorn,
sqlalchemy, psycopg2-binary, python-dotenv, python-jose, bcrypt, pydantic, email-validator,
python-multipart), requirements.txt, database.py (SQLAlchemy engine/session, identical pattern
to Project 5), .env (new Neon Postgres database created by the user for this project, plus a
freshly generated SECRET_KEY -- clarified for the user that SECRET_KEY is not something Neon
provides, it's a locally generated random value used only for signing JWTs), and .gitignore.

Built models.py (User, PasswordResetToken -- Conversation/ConversationParticipant/Message
deliberately deferred to the next step to keep this one focused on auth), schemas.py, auth.py
(copied verbatim from Project 5's hash_password/verify_password/create_access_token/
get_current_user, since JWT auth is explicitly reused as-is), and main.py with five endpoints:
POST /signup, POST /login (OAuth2PasswordRequestForm-based), POST /forgot-password (generates
a random token via secrets.token_urlsafe, stores it with a 30-minute expiry, and returns it
directly in the response body since there's no email service), POST /reset-password (validates
token + expiry + used flag, updates the password, marks the token used), and GET /me.

Bug hit and resolved: first uvicorn run showed "Application startup complete" (server actually
came up fine, connected to Neon correctly) but the browser then failed with
ERR_CONNECTION_REFUSED -- turned out to be Ctrl+C accidentally killing the server in that
terminal right after startup, not an actual code or config problem. Second run left alone
resolved it immediately.

Verified end-to-end in Swagger UI (/docs): /signup created a user, /login returned a JWT,
/forgot-password returned a reset token, /reset-password consumed it and updated the password
successfully.

Also cleaned up a stray empty frontend/ folder that had ended up nested inside backend/
(misplaced, not yet needed at this stage) -- deleted by the user in VS Code.
