## Conversations + messages REST layer (continued)

Built Conversation, ConversationParticipant, and Message models (a join-table pattern --
first time this pattern's been needed, since 1:1 and group chats are both just conversations
with N participants). Added POST /conversations, GET /conversations, POST
/conversations/{id}/messages, GET /conversations/{id}/messages, all protected and
membership-checked. Explained to the user why some responses need manual serialization
(schemas.ConversationOut assembled by hand via a serialize_conversation() helper) rather than
plain Pydantic from_attributes, since participants live in a separate join table.

Verified end-to-end in Swagger: created a second test user (testuser2), created a 1:1
conversation between testuser1 and testuser2, posted and listed messages successfully.

Bug/gap found by the user: POST /conversations created a brand-new conversation every time
instead of reusing an existing 1:1 thread between the same two people. Fixed by adding a
dedup check (a join + group-by-count-distinct query) that looks for an existing non-group
conversation containing exactly both users before creating a new one. Verified: calling
POST /conversations twice for the same pair now returns the same conversation id both times.

## WebSocket live messaging

Added a WebSocket endpoint (/ws/conversations/{id}) so messages appear instantly for other
participants without polling. Introduced an in-memory ConnectionManager (conversation_id ->
list of active sockets) and a get_user_from_token() helper, since the JWT has to be passed as
a query param (?token=...) rather than an Authorization header -- browsers can't attach
custom headers to a WebSocket handshake. Noted for the user that this in-memory approach only
works with a single backend server process, which is fine for now but worth revisiting if the
app is ever scaled to multiple instances.

Bug hit and fixed: the endpoint originally called websocket.close() with a custom code before
calling accept() when auth/membership checks failed -- Starlette/uvicorn can't deliver a real
close-reason code before the handshake is accepted, so the browser just saw a generic
abnormal-closure 1006 with no useful information. Fixed by accepting first, then closing with
4001 (bad token) or 4003 (not a participant) if the checks fail.

Bug hit and fixed: first WebSocket connection attempt 404'd with "No supported WebSocket
library detected" in the uvicorn logs -- plain `uvicorn` doesn't bundle WebSocket support.
Fixed with `pip install websockets` and a requirements.txt refresh.

Built a small standalone ws_test.html page (not part of the app) to test WebSockets directly,
since Swagger's /docs can't exercise them -- lets two browser tabs each hold a JWT and connect
to the same conversation. Verified real live delivery: a message typed in one tab appeared
instantly in the other tab (and vice versa) with no refresh.

Bug hit and fixed: an instruction to "update the <script> block" in ws_test.html was
ambiguous and the user replaced the entire file with just the <script> tag, losing the page's
HTML structure (blank page, no visible inputs). Fixed by resupplying the complete file.

## Presence (online/offline)

Added last_seen (nullable DateTime) to the User model. First schema change to an *existing*
table rather than a new one -- explained to the user that Base.metadata.create_all() only
creates missing tables, it won't add a missing column to a table that already exists, so a
manual `ALTER TABLE users ADD COLUMN last_seen TIMESTAMP;` was run directly in Neon's SQL
Editor before restarting the server (acceptable since it's still test data, not a real
migration tool situation yet).

Added a separate global /ws/presence WebSocket endpoint (connected once per app session, not
per-conversation) plus a PresenceManager tracking which user_ids are currently connected.
On connect/disconnect it broadcasts a presence event only to "contacts" -- other users who
share at least one conversation with this user -- rather than to everyone globally. On
disconnect, last_seen is stamped. Also added GET /conversations/{id}/presence as a plain REST
fallback for a client's initial page load, before its WebSocket connects.

Extended ws_test.html to open both the conversation socket and the presence socket together
on Connect, logging presence events inline with chat messages for easy testing.

Verified end-to-end with two tabs: connecting testuser2 in tab 2 correctly logged
"testuser2 is ONLINE" in tab 1; closing tab 2 correctly logged "testuser2 is OFFLINE" in
tab 1 shortly after.
## Image/file sharing (Cloudinary)

Added Cloudinary as the attachment store, since Render's free tier has no persistent disk
between deploys -- files uploaded to the backend's own filesystem wouldn't survive a redeploy.
Added `attachment_url`, `attachment_type`, and `attachment_public_id` columns to Message
(`public_id` specifically kept so a later delete-for-everyone could clean the file up on
Cloudinary's side, not just remove the database row). Added
`POST /conversations/{id}/messages/upload` (multipart, `UploadFile` + optional caption),
which detects image vs. other file by content-type, uploads to Cloudinary under a
per-conversation folder (`project6-chat/conversation_{id}`), and broadcasts the resulting
message over the same WebSocket connection manager used for text messages -- so an uploaded
image/file appears live for other participants exactly like a typed message does, no separate
code path needed on the receiving end.

Frontend got a file-picker + send flow on the message composer, with image attachments shown
inline and other file types shown as a download link. Verified end-to-end: sent an image from
one browser tab, saw it appear instantly (no refresh) in a second tab logged in as the other
participant.

## Delete-conversation (delete-for-me / delete-for-everyone)

Added WhatsApp-style delete as two deliberately different endpoints, not one endpoint with a
flag. `DELETE /conversations/{id}/me` just stamps `deleted_at` on that user's own
`ConversationParticipant` row -- non-destructive, the conversation and its messages are
untouched for every other participant, it just stops showing in this one user's list.
`DELETE /conversations/{id}` (delete-for-everyone) actually deletes the `Conversation` row
(cascading to participants and messages), but first loops over every message in it that has
an `attachment_public_id` and calls `cloudinary.uploader.destroy()` on each one, so attached
files don't sit orphaned in Cloudinary storage after the conversation referencing them is
gone. Frontend added a per-conversation menu (three-dot / long-press style) exposing both
options separately, since they're not the same action and shouldn't be offered as one
ambiguous "Delete" button.

## Group chat: missing feature found and fixed

After deployment, real usage surfaced: "we are able to use 1-2-1 but not able to use for
group." Investigation found this wasn't a bug in existing code at all -- the backend had
fully supported group conversations from day one (`is_group` flag, a list of
`participant_usernames`, an optional group `name`), but the frontend's "start chat" form had
only ever been built to send a single username, with `is_group` always defaulting to false.
There was simply no UI path to create a group. Clarified group-creation UX with the user
first (separate "+ New Group" button vs. inline toggle; group name required vs. optional) --
chose a separate button and a required name -- then added the form directly to
`app/page.js` at the user's explicit request for that one instance (state for
`showGroupForm`/`groupName`/`groupUsernames`, a `handleCreateGroup` handler calling
`createConversation` with `is_group: true` and a comma-separated username list, and the
toggle + form JSX itself). Verified working end-to-end with a real 3-person group named
"Gyanyaan."

## Stale service worker: root-caused and fixed

Two separate-looking reports turned out to share one root cause. First: "someone else created
the group but now not visible to me" (turned out to be a page-load-timing question, not an
actual bug -- the group was visible in the screenshot). Then, more concretely: "not able to
see the create group option" on a device that should have had the feature already deployed.
Diagnosed as the service worker's original cache-first strategy serving an old cached JS
bundle from before the group-chat UI shipped -- because browsers only re-check a service
worker for updates by comparing `sw.js` itself, byte-for-byte, an unrelated app-code deploy
doesn't trigger any re-check at all, so a user who already had the app open or installed could
be stuck on stale JS indefinitely. Immediate workaround given (hard-refresh, or unregister +
clear Cache Storage in DevTools) unblocked the user immediately.

For the actual fix ("fix this," not just a workaround), rewrote `sw.js`'s fetch handler from
cache-first to network-first with cache fallback: always try the real network first, cache
successful GET responses as a backup, and only serve from cache if the fetch itself fails
(genuinely offline). Chose this over building a full "update available" banner +
`skipWaiting()`/`postMessage()` flow, which was considered but judged unnecessary extra
complexity for this app's actual needs. User applied, committed, and tested this fix
themselves; confirmed working with "all ok now."
