Project 6 of 10 · Anatomy

Real-Time Chat App (1:1 + Group, PWA)

A WhatsApp/Telegram-style chat app built on top of Project 5's auth foundation: 1:1 and group conversations, live messaging over WebSockets, online/offline presence, image/file sharing via Cloudinary, and WhatsApp-style delete-for-me / delete-for-everyone — packaged as an installable PWA and deployed for real, then hardened against a genuine stale-cache bug hit twice in production.

Next.js PWA→ FastAPI + JWT + WebSockets→ Postgres · Vercel+Render+Neon+Cloudinary

Overview

Projects 4 and 5 built a solid three-tier, authenticated foundation. Project 6's job was to make the app live — messages appear on other people's screens the instant they're sent, not on next page load — and to model something genuinely more complex than a single owner's rows: a conversation with multiple participants, some of whom can see it and some of whom can't (once they've deleted it for themselves), carrying messages that might have an attached file living on a third-party host.

Scope, agreed up front: 1:1 and small-group conversations, JWT auth reused from Project 5, an in-app password-reset flow (no email service — the reset token is displayed directly), online/offline presence, and image/file sharing. Typing indicators and read receipts were explicitly deferred. The app had to work as an installable PWA across web, Windows, Mac, and Android, and needed a delete-conversation feature matching WhatsApp's two-mode behavior.

Same three-tier shape as Project 5, but Tier 2 now speaks two protocols: normal HTTP for everything that fits request/response (signup, login, listing conversations, sending an image), and WebSockets for the two things that genuinely need to push data unprompted — new messages and presence changes. A fourth party, Cloudinary, sits off to the side purely for file storage; the backend never stores attachment bytes itself, only the URL Cloudinary hands back.

Data model

Four tables carry the whole app. The join-table shape (ConversationParticipant sitting between Conversation and User) is the one genuinely new modeling decision this project — it's what lets a conversation scale from exactly two people to any number of group members without a schema change, and it's what makes "delete for me" possible as a per-row flag instead of a per-conversation one.

Message + presence flow

1
Client opens a WebSocket per open chatwss://.../ws/conversations/5?token=<jwt> — token passed as a query param since the browser WebSocket API can't set headers
2
Backend accepts first, then verifiesawait websocket.accept() always runs before the token check, so a rejected client gets a clean close code instead of a generic 1006 error
3
Connection is registered in memoryConnectionManager keeps {conversation_id: [sockets]} as a plain dict — transient state, not written to Postgres
4
A message is sentSaved to the messages table first (the durable copy), then broadcast to every other open socket on that same conversation_id
5
Presence connects separatelyA second WebSocket (/ws/presence) tracks who's online; on connect/disconnect it broadcasts only to that user's "contacts" — other users sharing at least one conversation
6
Disconnect updates last_seenWhen a presence socket closes, the user's users.last_seen row is updated so "Last seen ..." can be shown even while offline

Key concepts

Real-time

WebSockets

One persistent, bidirectional connection instead of repeated request/response HTTP calls.

Auth

Query-param JWT

Browser WebSockets can't send custom headers, so the token rides in the connection URL instead.

Protocol

Accept-before-close

Always accept the handshake first, then reject with a real close code — avoids opaque 1006 errors.

State

In-memory connection managers

Who's connected right now lives in server memory, not the database — correctly ephemeral.

Schema

Join-table conversations

ConversationParticipant scales a "conversation" from 2 people to any group, with no schema change.

Storage

Cloudinary for attachments

Files live on a third-party host, referenced by URL — never stored on the backend's own disk.

Service worker: cache-first → network-first

Project 5's service worker cached the app shell cache-first — fine for a to-do/notes app whose shell barely changes. This project exposed the real problem with that choice: a browser only re-checks a service worker for updates by comparing sw.js itself, byte-for-byte. If sw.js's own content never changes, the old worker — and its caching strategy — keeps running forever, no matter how many times the rest of the app gets redeployed. Two separate bug reports this project ("group option missing," "new group not visible") both traced back to exactly this: users who already had the app open were being served stale, pre-feature JS.

StrategyBehaviorFailure mode
Cache-first (Project 5)Serve from cache immediately, never re-check networkSilently stale forever after any deploy that doesn't touch sw.js itself
Network-first (Project 6 fix)Try the network first; cache successful responses; fall back to cache only if the fetch failsNone for staleness — small latency cost per request, acceptable for this app

The alternative considered and deliberately not built was a full "update available" flow — detecting a waiting worker, showing a banner, and calling skipWaiting() + postMessage() on user confirmation. Network-first was chosen instead as the simpler fix that fully solves the actual problem (staleness) without that extra UI machinery, which wasn't judged necessary for this app's needs.

Bugs, debugged for real

Every one of these was an actual failure hit mid-build, not a scripted lesson.

device_bash mount-path mismatch

Writing directly to the absolute path device_list_dir reported failed with "No such file or directory" — device_bash needed the $HOME/mnt/<folder-name>/... mount prefix instead, a different path to the exact same files.

PWA stuck on "Loading..." in dev mode

Same root cause as Project 5's dev-mode issue, hit again: the cache-first service worker conflicted with next dev's hot-reload bundle hashes. Fixed by only registering the service worker in production builds, verified via next build && next start.

Group chat "not working" — a missing feature, not a bug

The backend fully supported group conversations from the start (is_group, a list of usernames, an optional name); the frontend's "start chat" form simply never had a way to create one. Fixed by adding a "+ New Group" toggle and form.

Recurring "can't see the feature" reports — stale service worker

Traced to the cache-first strategy described above: users with the app already open kept seeing pre-feature JS after successful deploys. Root-caused and fixed by switching to network-first, rather than relying on a manual unregister-and-hard-refresh workaround each time.

Transient Render /openapi.json 404

Swagger briefly reported "Failed to load API definition" right after a deploy. Render's logs showed a container-restart blip around the same time; resolved on a simple retry, no code change needed.

CORS blocked the deployed frontend

Same class of bug as every prior deployed project: the backend's allow_origins needed the real Vercel production URL added. Separately confirmed that a per-deployment Vercel preview URL correctly fails CORS, since only the exact production origin is allowlisted.
