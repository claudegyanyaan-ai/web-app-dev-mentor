Build checklist

  • JWT auth reused from Project 5, plus in-app password reset (token displayed directly, no email service)
  • Conversation / ConversationParticipant / Message schema supporting both 1:1 and group chats via one join-table design
  • 1:1 conversation dedup (join + group_by + having) — group conversations deliberately skip dedup
  • Live messaging via WebSocket (/ws/conversations/{id}), JWT passed as a query param, accept-before-close pattern
  • Online/offline presence via a separate WebSocket (/ws/presence), scoped only to users who share a conversation ("contacts")
  • Image/file sharing via Cloudinary, with public_id tracked per message for later cleanup
  • Delete-for-me (per-user, non-destructive) and delete-for-everyone (real delete + Cloudinary attachment cleanup) as separate endpoints
  • Group chat creation UI: "+ New Group" form (name required, comma-separated usernames)
  • PWA packaging: manifest.json, service worker, production-only registration guard (dev-mode hot-reload lesson carried over from Project 5)
  • Deployed as two services — backend to Render, frontend to Vercel — CORS updated, tested live with 3 real accounts across machines
Missing feature, not a bug — group chat UI: the backend already fully supported groups; the frontend simply never had a form to create one. Added a "+ New Group" toggle with a group-name and comma-separated-usernames form.
Bug fixed — stale service worker after every deploy: the cache-first service worker kept serving old cached JS to users who already had the app open, even after successful deploys, because browsers only re-check a service worker by comparing sw.js byte-for-byte. Root-caused and fixed by switching to network-first with cache fallback.
Bug fixed — transient Render /openapi.json 404: Swagger briefly failed to load its API definition right after a deploy; logs showed a container restart blip, resolved on retry with no code change.
Bug fixed — CORS: same class of bug as every prior deployed project — the real Vercel production URL had to be added to the backend's allow_origins list.

Concepts introduced

Full plain-English explanations in CONCEPTS.md. Summary:

  • WebSockets — a persistent, bidirectional connection, vs. request/response HTTP
  • Authenticating a WebSocket via a query-param JWT (no custom headers available)
  • The accept-before-close pattern — avoids generic 1006 errors on rejected connections
  • In-memory connection managers for transient state (who's online right now), separate from the database
  • Conversation / ConversationParticipant / Message join-table design for 1:1 and group chats alike
  • 1:1 dedup vs. deliberately allowing duplicate groups
  • Presence scoped to "contacts" (shared-conversation users), not broadcast globally
  • Cloudinary for file/image storage, with public_id tracked for later cleanup
  • Delete-for-me vs. delete-for-everyone as genuinely different operations
  • Cache-first vs. network-first service worker strategy, and why sw.js updates aren't auto-detected

Checkpoint quiz

1. What does a WebSocket give you that a normal HTTP request can't, and why does live chat need it?
2. Why is the chat's JWT passed as a query parameter instead of an Authorization header for the WebSocket connection?
3. Why does the app use a Conversation + ConversationParticipant join table instead of just a user_a_id/user_b_id pair on each conversation?
4. Why does 1:1 conversation dedup exist, but group conversations deliberately skip it?
5. Why did the group chat feature "not work" even though the backend already fully supported it — and separately, why did users keep seeing stale content after later deploys?

Answered verbally in the mentoring session — see debrief.
