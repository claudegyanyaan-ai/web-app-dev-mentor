02What HTML actually is

HTML (HyperText Markup Language) is not a programming language — it has no logic, no calculations, no "if this then that." It's a markup language: it wraps content in tags that say what each piece of content is.

When the browser reads <h1>Hi, I'm VT.</h1>, the tags tell it "this text is the top-level heading" — not what color it should be or how big. That's the whole job of HTML: naming the parts. We used semantic tags specifically — <header>, <nav>, <main>, <section>, <footer> — instead of generic <div>s everywhere, because a screen reader, a search engine, and another developer reading the code all get real information from a tag named <nav> that a <div class="nav"> only gives them if they read the class name too.

CSS and JavaScript then attach to that structure from the outside — CSS via tag names and classes, JavaScript via the same selectors. HTML is the skeleton everything else hangs off of.

03Is this a page, or a website?

Worth being precise about, since the terms get used interchangeably but mean different things.

What we built

A single-page site

One file — index.html — with four sections (Hero, About, Projects, Contact) stitched together on one scrolling page. Clicking "About" in the nav doesn't load a new page; it jumps to an anchor (#about) further down the same document.

What we didn't build (yet)

A multi-page website

Separate HTML files — about.html, projects.html — or, in a framework, separate routes, each a distinct URL the browser actually navigates to. Project 3 (React/Next.js) introduces real routing.

Rule of thumb: if the URL in the address bar changes when you click a link, you've moved to a different page. Ours never changes — that's the signature of a single-page site.

04What this project actually covered

Small as it looks, Project 1 touched six distinct disciplines — the same six that show up in every real web project, just at the smallest possible scale.

Structure

  • Semantic HTML — header/nav/main/section/footer
  • Anchor-link navigation (zero-JS routing)
  • Meta tags: viewport, description

Styling

  • CSS reset — killing inconsistent browser defaults
  • Flexbox for the nav layout
  • Media queries — the actual mechanism behind "mobile-responsive"

Behavior

  • DOM selection — querySelector
  • Events — addEventListener
  • classList.toggle() for the mobile menu

Debugging

  • Reading DevTools' Network tab for a missing/broken file
  • Diagnosing "silent" HTML failures (a missing <head> throws no error)
  • Telling real changes apart from line-ending noise

Version control

  • Git basics — init, add, commit, push
  • One combined repo for all 10 projects
  • Why rewriting pushed history is a "stop and ask" moment

Tooling & deploy

  • A custom code-explainer subagent
  • A post-commit push-reminder hook
  • Free-tier hosting via Vercel + GitHub

05How the deployment actually works

"Deploying" just means: put the files somewhere the public internet can reach, over HTTPS, at a stable address. Here's what's actually happening behind that one click.

1
Vercel connects to GitHub via OAuthSigning in with "Continue with GitHub" links your Vercel account to your claudegyanyaan-ai identity — no separate password.
2
A webhook gets installed on the repoVercel subscribes to "notify me on every push" — this is the piece that makes redeploys automatic later.
3
Root Directory scopes the deploySince this repo holds all 10 projects, we pointed Vercel at project-1-portfolio specifically — otherwise it would try to serve the whole repo as one site.
4
No build step, because there's nothing to buildPlain HTML/CSS/JS ships as-is. (Projects 3+ introduce an actual build step, once React enters the picture.)
5
A live URL is assigned, HTTPS included freeweb-app-dev-mentor-projec1.vercel.app — reachable by anyone, anywhere, with a padlock in the address bar by default.

What "auto-deploy" means going forward: every future git push to main triggers that webhook again — Vercel rebuilds and republishes to the same URL automatically. No manual redeploy step, ever, unless you're changing infrastructure settings like the Root Directory.

06Commands reference

The actual commands run this session, grouped by what they were for.

Repo setup

git init# turns this folder into a git repository mkdir project-1-portfolio mkdir chat-logs

Connecting to GitHub

git branch -M main git remote add origin https://github.com/claudegyanyaan-ai/web-app-dev-mentor.git git push -u origin main# -u links local "main" to origin's "main" for future plain pushes

The everyday commit loop

git status# what changed? git add .# stage everything changed git commit -m "message"# save a checkpoint git push# send it to GitHub → triggers Vercel redeploy

Undoing a mistake safely

git diff -w --stat# check if a "change" is real, or just line-ending noise git checkout -- .# discard uncommitted changes, restore last commit's version
