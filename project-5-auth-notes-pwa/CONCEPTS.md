# Project 5 Concepts — Auth-Enabled Task & Notes App (PWA)

Plain-English notes on everything new in this project. Project 4's three-tier architecture,
FastAPI/SQLAlchemy/CORS, and deployment concepts still apply and aren't repeated here.

## 1. Password hashing with bcrypt
A password must never be stored as plain text -- if the database ever leaks, every account
leaks with it. bcrypt turns a password into a one-way scrambled string (`hashed_password`,
starting `$2b$12$...`) that cannot be reversed back into the original password.
`bcrypt.hashpw()` creates the hash at signup; `bcrypt.checkpw()` at login re-hashes the
typed password and compares it to the stored hash -- the plain password itself is never
stored or compared directly.

## 2. JWT (JSON Web Tokens) and stateless auth
After a successful login, the backend doesn't remember "this user is logged in" anywhere --
instead it hands back a signed token (a JWT) containing the user's id (`sub` claim) and an
expiry time, encoded and signed with a secret key (`SECRET_KEY`) only the backend knows.
The frontend stores this token (`localStorage`) and sends it back on every future request
in an `Authorization: Bearer <token>` header. The backend re-verifies the signature on every
request (`jwt.decode`) -- if the signature doesn't match or the token expired, the request
is rejected with 401. No server-side "session" is stored anywhere; the token itself IS the
proof of identity.

## 3. FastAPI dependency injection for auth: `Depends(get_current_user)`
`auth.py`'s `get_current_user()` function extracts and verifies the JWT, then looks up the
matching `User` row. Every protected endpoint declares
`current_user: models.User = Depends(auth.get_current_user)` as a parameter -- FastAPI runs
that function automatically before the endpoint's own code, and if it raises (bad/missing
token), the endpoint's code never runs at all. This is the entire mechanism that turns
`/tasks` from "everyone's tasks" into "only YOUR tasks."

## 4. Per-user data isolation
Every protected query is filtered by the logged-in user's id, not just their existence:
`db.query(models.Task).filter(models.Task.user_id == current_user.id)`. Without this filter,
a valid token would let any logged-in user see or edit *everyone's* data -- authentication
(who are you) and authorization (what are you allowed to touch) are two separate concerns,
and this filter is the authorization half.

## 5. Foreign keys and relationships
This project introduces genuine multi-table relationships for the first time. `Task.user_id`
and `Note.user_id` are `ForeignKey("users.id")` columns -- each task/note row points at
exactly one user row, and Postgres itself enforces that the referenced user actually exists.
SQLAlchemy's `relationship()` (`User.tasks`, `Task.owner`) is a convenience layer on top of
that foreign key, letting Python code navigate `some_user.tasks` or `some_task.owner`
without writing a JOIN by hand.

## 6. The JSON column type (checklist items)
A checklist note needs a list of items, each with its own text and done-state. Rather than
create a whole separate `checklist_items` table, `Note.items` is a `JSON` column that stores
the entire list directly: `[{"text": "milk", "done": false}, ...]`. This is a deliberate
tradeoff -- simpler to build, but the items aren't individually queryable/indexable the way
a real table's rows would be. Fine for a personal notes app; a different call for something
at much larger scale.

## 7. `server_default=func.now()` and `onupdate=func.now()`
Automatic timestamps generated by the DATABASE itself, not the application code:
`created_at = Column(DateTime(timezone=True), server_default=func.now())` sets the value at
INSERT time; adding `onupdate=func.now()` (used on `updated_at`) re-sets it on every UPDATE.
This is more reliable than setting timestamps in Python, since it can't be forgotten in some
code path and stays correct even if a row is edited directly in the database.

## 8. PWA: manifest.json
A plain website becomes an installable app via two files. `manifest.json` describes the app
to the OS/browser: its name, icon(s), theme color, and `"display": "standalone"` -- which is
what makes an installed instance open in its own window with no browser address bar or
tabs, instead of just being a bookmark.

## 9. PWA: service workers
`sw.js` is a script that runs in the background, separate from the page itself, and can
intercept every network request the page makes (`self.addEventListener("fetch", ...)`).
This project's service worker caches the app shell (`/`, icons, manifest) on install so it
loads instantly on repeat opens, but deliberately passes API calls straight through to the
network uncached -- task/note data must always be fresh, never served stale from a cache.
Registering it (`navigator.serviceWorker.register("/sw.js")`) has to happen from
client-side JS, since it's a browser API with no server equivalent.

## 10. Cross-device sync is really just "the same backend, multiple clients"
Nothing special was built for cross-device sync -- it's an emergent property of the
architecture already in place. Any device that logs in with the same account hits the same
Render backend and the same Neon database, so it sees the same data. The JWT is
device-specific (each login on each device gets its own token), but the underlying account
and data are shared.

## 11. Bugs debugged this project (real lessons, not scripted)
- **Windows venv moved to the wrong location, then broken by a physical move.** venv
  launcher scripts (`pip.exe`, `python.exe`) embed the venv's original absolute path --
  moving the folder breaks them. Fixed by deleting and recreating the venv directly in the
  correct location instead of moving it.
- **passlib + bcrypt 5.0.0 incompatibility.** passlib (unmaintained since 2020) crashed
  trying to read a `bcrypt.__about__.__version__` attribute that bcrypt 5.0 removed --
  surfaced as `AttributeError` then a confusing `ValueError: password cannot be longer than
  72 bytes`. Fixed by dropping passlib entirely and calling `bcrypt.hashpw`/`bcrypt.checkpw`
  directly.
- **Case-sensitive import on Windows.** A component saved as `Taskitem.js` (lowercase i)
  broke `import TaskItem from "./TaskItem"` at build time -- Windows' filesystem is
  case-insensitive but Turbopack's module resolution isn't. Same class of bug as Project 3.
- **Dark-mode CSS made the page unreadable.** `create-next-app`'s default
  `@media (prefers-color-scheme: dark)` block flipped the page background to near-black on
  a dark-mode OS/browser while the app's own Tailwind text classes stayed dark. Fixed by
  removing that media block so the page always renders light.
- **Stale service-worker cache in dev mode.** The installed app got stuck on "Loading..."
  even with the dev server running, because the cache-first service worker had served a
  broken cached copy of Next.js's dynamically-regenerated dev-mode JS chunks. Fixed by
  unregistering the service worker and clearing site data -- a dev-server-only failure mode
  that goes away once pointed at a real deployed production build.
- **`pip freeze` run without the venv activated** captured unrelated global-Python packages
  instead of the project's actual dependencies. Caught by checking for the `(venv)` prefix
  in the terminal prompt before trusting the output.
- **Vercel's Root Directory folder-picker saved the wrong path.** A cut-off browser modal
  caused just `frontend` to get saved instead of the full nested
  `project-5-auth-notes-pwa/frontend`, failing the first deploy attempt. Fixed by deleting
  and re-importing the project, this time confirming the full path before deploying.
- **CORS blocked the deployed frontend** (same class of bug as Project 4) until the real
  Vercel URL was added to the backend's `allow_origins` list and Render was redeployed.
