## Backend build
Built backend/database.py (SQLAlchemy engine/session setup, same pattern as Project 4, plus
a shared get_db() dependency), .env (DATABASE_URL from the new Neon p5 project + a locally
generated SECRET_KEY for JWT signing -- first project needing a SECRET_KEY, since Project 4
had no auth), and .gitignore.

Built backend/models.py: three tables -- User (id, email, hashed_password, created_at),
Task (extended from Project 4 with user_id ForeignKey, due_date, created_at, updated_at),
and Note (id, user_id ForeignKey, type, title, content, items [JSON column for checklist
items], color, pinned, archived, created_at, updated_at). First project introducing
ForeignKey and relationship().

Built backend/schemas.py: Pydantic schemas for User/Token (auth), Task (extended), and Note
(new) -- same models.py-vs-schemas.py separation taught in Project 4.

Built backend/auth.py: password hashing, JWT creation, and get_current_user dependency
(the "protected route" gatekeeper).

Bug: passlib + bcrypt 5.0.0 incompatibility. passlib (last released 2020, unmaintained)
crashes trying to read a bcrypt version marker that bcrypt 5.0 removed, throwing
"AttributeError: module 'bcrypt' has no attribute '__about__'" and ultimately
"ValueError: password cannot be longer than 72 bytes" during signup. Diagnosed via the
uvicorn terminal traceback. Fixed by dropping passlib entirely and calling the bcrypt
library directly (bcrypt.hashpw / bcrypt.checkpw) -- same underlying hashing algorithm,
no unmaintained middleman. Verified fixed: /signup and /login both tested successfully in
Swagger after the fix, real bcrypt hash confirmed in Neon's users table ($2b$12$... format).

Built backend/main.py in three passes:
1. App setup + Base.metadata.create_all (now creates users/tasks/notes tables) + CORS +
   /signup + /login (OAuth2PasswordRequestForm-based, gives Swagger a built-in Authorize
   login form)
2. Protected /tasks CRUD (GET/POST/PUT/DELETE), each requiring get_current_user and filtered
   by user_id -- this is the actual per-user data isolation mechanism
3. Protected /notes CRUD (GET/POST/PUT/DELETE), same pattern, supporting both plain-text and
   checklist note types plus color/pinned/archived updates

Full backend tested end-to-end in Swagger: signup, login (via Swagger's Authorize dialog),
GET /tasks unauthenticated correctly returns 401, POST/GET tasks work once authorized,
POST /notes tested with both a plain-text note (color yellow) and a checklist note (color
blue, two items with independent done states), GET /notes confirms both return correctly.

Backend for Project 5 (auth + tasks + notes, fully protected and per-user) is complete.

## Frontend build (continued from above)

Next.js scaffolded inside project-5-auth-notes-pwa/frontend (JavaScript, ESLint, Tailwind,
no src/, App Router -- same options as Projects 3/4). One false start: first
`npx create-next-app@latest` run (missing the trailing dot) prompted for a project name and
created a stray `my-app` folder; immediately redone correctly with
`npx create-next-app@latest .` and confirmed no leftover folder. `npm run dev` verified
working on Next.js 16.3.3 with Turbopack.

Built lib/api.js: a shared apiFetch() wrapper that reads the JWT from localStorage, attaches
it as an Authorization: Bearer header on every request, and auto-redirects to /login on a
401 response. Exposes signup(), login() (stores the token on success), logout(), and
CRUD helpers for both tasks and notes. .env.local holds NEXT_PUBLIC_API_URL pointing at the
local backend.

Built app/login/page.js and app/signup/page.js (client components, form-based, redirect to
"/" on success). Bug hit during testing: signup showed a generic "Signup failed" error with
no explanation -- traced via DevTools Console/Network to net::ERR_CONNECTION_REFUSED, which
turned out to mean the uvicorn backend simply wasn't running (not a code bug). Restarting
uvicorn fixed it; signup + login then worked end-to-end and the JWT was confirmed present in
localStorage.

Rebuilt the Tasks UI for auth + due dates: AddTaskForm.js gained a due-date input,
TaskItem.js now displays the due date when set, and app/page.js was rewritten to check for a
token on load (redirecting to /login if missing), fetch tasks via getTasks(), and wire
create/toggle/edit/delete through the api.js helpers plus a logout button.

Two real bugs hit and fixed while wiring the Tasks UI:
1. Build error "Module not found: Can't resolve './TaskItem'" -- caused by the file actually
   being saved as `Taskitem.js` (lowercase i) instead of `TaskItem.js`. Same class of
   case-sensitivity bug as Project 3's Components/components folder issue (Windows
   filesystem is case-insensitive but Turbopack's module resolution is not). Fixed by
   renaming the file to the exact case.
2. Page rendered but text was almost invisible (dark text on a near-black background) --
   caused by create-next-app's default `@media (prefers-color-scheme: dark)` block in
   globals.css flipping the page background to near-black on a dark-mode OS/browser, while
   the app's own Tailwind text classes stayed dark. Fixed by removing that dark-mode media
   block from globals.css so the page always renders light. Confirmed fixed via screenshot:
   white background, readable heading, tasks showing with correct due dates (e.g.
   "Due 8/30/2026").

Task #42 marked completed.

Bug hit right after: reopening the installed app showed a stuck "Loading..." screen even
with both npm run dev and uvicorn running. Root cause: the service worker's cache-first
strategy had served a stale/broken cached copy of Next.js dev-mode JS chunks (Turbopack's
dev server regenerates these dynamically, which doesn't play well with aggressive caching).
Fixed by unregistering the service worker and clearing site data in DevTools -> Application,
which also cleared localStorage (so a fresh login was needed after, which is expected, not a
bug). Noted this is a dev-server-specific quirk -- once deployed, the installed app will
point at the real production URLs instead of a locally-running dev server, which removes
this failure mode.
