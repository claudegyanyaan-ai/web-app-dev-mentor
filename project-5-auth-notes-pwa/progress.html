Build checklist

  • Scope extended beyond the default plan (user request): Google Keep-style sticky notes, automatic timestamps, cross-device sync via login
  • Neon Postgres database (separate project) with users, tasks, notes tables — foreign keys + relationships
  • Password hashing with bcrypt, JWT-based login (signup/login endpoints, OAuth2PasswordBearer)
  • Every protected endpoint filtered by current_user.id — real per-user data isolation, verified via a 401 on an unauthenticated request
  • Tasks CRUD with due dates and automatic created/updated timestamps
  • Notes CRUD: text and checklist types, color picker, pin, archive — JSON column for checklist items
  • Frontend auth flow: signup/login pages, token stored in localStorage, auto-redirect to /login on 401
  • PWA packaging: manifest.json, service worker (network-first for API calls, cache-first for the app shell), custom icon set generated from the user's own logo
  • Installed and verified on both desktop (Windows/Chrome) and mobile (Android/Chrome)
  • Deployed as two services — backend to Render, frontend to Vercel — CORS updated, verified live end-to-end including cross-device login/sync
Bug fixed — passlib/bcrypt incompatibility: unmaintained passlib crashed against bcrypt 5.0. Fixed by calling bcrypt.hashpw/bcrypt.checkpw directly instead.
Bug fixed — case-sensitive import + dark-mode CSS: a component filename case mismatch and the default dark-mode media query both broke the Tasks page after Project 3's exact same import lesson — same root cause, different project.
Bug fixed — stale service-worker cache in dev mode: the installed app got stuck loading against locally-running dev servers; resolved by clearing the service worker cache (a dev-only failure mode, gone once deployed).
Bug fixed — Vercel Root Directory + CORS: a cut-off folder-picker modal saved the wrong root directory on the first deploy attempt; and, as in Project 4, the backend's CORS allow-list needed the real deployed frontend URL added before the live app could talk to the live backend.

Concepts introduced

Full plain-English explanations in CONCEPTS.md. Summary:

  • Password hashing with bcrypt — never store plain-text passwords
  • JWT — stateless, signed tokens as proof of identity, verified on every request
  • FastAPI dependency injection (Depends) for auth — get_current_user gates every protected endpoint
  • Per-user data isolation — filtering every query by the logged-in user's id
  • Foreign keys and SQLAlchemy relationships — real multi-table structure for the first time
  • The JSON column type — storing a whole checklist as one column, tradeoffs vs. a real table
  • Database-generated timestamps (server_default / onupdate)
  • PWA manifest.json and standalone display mode
  • Service workers — background caching, and why API calls must bypass the cache
  • Cross-device sync as an emergent property of shared backend + database, not new code

Checkpoint quiz

1. Why is a password hashed instead of encrypted — what's the practical difference for this app?
2. What actually stops User A from seeing User B's tasks, given both have valid, currently-logged-in JWTs?
3. What is a foreign key, and what does Task.user_id = ForeignKey("users.id") actually enforce?
4. Why does the service worker deliberately NOT cache requests to the backend API?
5. No "sync" code was written anywhere. Why does logging in on your phone show the same tasks as your laptop?

Answered verbally in the mentoring session — see debrief.

What you could break/change next

  • Add a "forgot password" flow, or at minimum a password-change endpoint
  • Add a dedicated "Archived notes" view instead of archived notes just disappearing
  • Shorten the JWT expiry (currently 7 days) and add a refresh-token flow
  • Add offline write support — currently the service worker only caches reads; a true offline-first app would queue writes made while offline
