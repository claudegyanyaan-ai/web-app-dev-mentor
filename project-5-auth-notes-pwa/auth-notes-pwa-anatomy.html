Project 5 of 10 · Anatomy

Auth-Enabled Task & Notes App (PWA)

Project 4's three-tier app, now with real accounts: passwords are hashed, every request proves identity with a signed token, and every piece of data belongs to exactly one user. Extended beyond the default brief into a Google Keep-style notes app, then packaged as an installable PWA that runs identically on Windows, Android, and — by the same mechanism — Mac and iOS.

Next.js PWA→ FastAPI + JWT→ Postgres · Vercel+Render+Neon

Overview

Project 4 proved a real three-tier system could work. Project 5's job was to make that system trustworthy for more than one person at a time — and then take it out of the browser entirely. Two mostly-separate lessons ended up in one project: authentication/authorization (who are you, and what are you allowed to touch), and PWA packaging (turning a website into something installable, with its own icon, its own window, and offline-friendly caching).

The scope also grew beyond the original brief mid-project, at the user's request: sticky notes (Google Keep-style, with colors, checklists, pin/archive) and automatic timestamps were added on top of the baseline "auth-enabled task app" plan, and cross-device sync — logging in on a phone and seeing the same data as on a laptop — turned out to require no new code at all, just the architecture already in place.

Same three-tier shape as Project 4, with one addition running alongside every request: a proof of identity. The frontend now carries a token on every call; the backend now verifies that token AND uses it to scope every database query to one specific user's rows.

Key concepts

Security

bcrypt password hashing

One-way hashing means even a full database leak doesn't expose real passwords.

Auth

JWT — stateless tokens

The signed token itself is the proof of login; no server-side session store needed.

FastAPI

Depends(get_current_user)

Dependency injection gates every protected endpoint before its own code ever runs.

Authorization

Per-user query filtering

A valid token proves WHO you are; filtering by user_id decides WHAT you can touch.

PWA mechanics

Two files turn a normal website into something installable. manifest.json tells the OS what the app is called, what icon to show, and — critically — "display": "standalone", which is what makes an installed instance open in its own window with no browser chrome at all. sw.js (the service worker) is a background script that intercepts every network request the page makes and decides, per-request, whether to answer from a cache or let it hit the real network.

Request typeStrategyWhy
App shell (/, icons, manifest)Cache-first, precached on installInstant repeat loads; the shell itself rarely changes
Backend API callsNetwork-only, never cachedTask/note data must always be current, never served stale

Registering the service worker (navigator.serviceWorker.register("/sw.js")) has to run in client-side JS — it's a browser API, so it lives in a small client component (RegisterSW.js) mounted from the root layout. Installability was verified two ways: locally against localhost (proves the mechanics work on one machine) and against the real deployed URL on an Android phone (proves it actually works as a genuine cross-device installable app, which is what matters).

Bugs, debugged for real

Every one of these was an actual failure hit mid-build, not a scripted lesson.

Windows venv broken by a physical move

The venv was first created one directory too high, then moved into place — which broke pip/python entirely, since Windows venv launcher scripts embed the venv's original absolute path. Fixed by deleting and recreating the venv directly in the correct location instead of moving it.

passlib + bcrypt 5.0.0 incompatibility

Unmaintained passlib crashed reading a bcrypt.__about__ attribute bcrypt 5.0 removed, surfacing as a confusing ValueError: password cannot be longer than 72 bytes. Fixed by dropping passlib and calling bcrypt.hashpw/bcrypt.checkpw directly.

Case-sensitive import + dark-mode CSS

A component saved as Taskitem.js (lowercase i) broke the build — the same case-sensitivity trap as Project 3. Separately, the default dark-mode media query in globals.css made the whole Tasks page nearly unreadable on a dark-mode browser; fixed by removing that block.

Stale service-worker cache in dev mode

The installed app got stuck on "Loading..." even with the dev server running, because the cache-first service worker had served a broken cached copy of Next.js's dynamically-regenerated dev-mode JS chunks. Fixed by unregistering the service worker and clearing site data — a dev-only failure mode, gone once pointed at a real deployed build.

Vercel Root Directory saved the wrong path

A cut-off browser modal for picking the Root Directory ended up saving just frontend instead of the full nested project-5-auth-notes-pwa/frontend, failing the first deploy. Fixed by deleting and re-importing the project, confirming the full path before deploying.

CORS blocked the deployed frontend

Same class of bug as Project 4: the backend's allow_origins only had localhost:3000 until the real Vercel URL was added and the backend redeployed.
