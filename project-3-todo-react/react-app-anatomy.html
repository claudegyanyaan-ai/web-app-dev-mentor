Project anatomy · recap

React To-Do Anatomy

Same to-do app, third rebuild — but this time the screen doesn't get manually redrawn at all. You describe what things should look like for a given set of data, and React handles making it happen. This doc walks through what changed and why.

01 The component tree

Instead of one file doing everything, the UI is now a small tree of components, each responsible for one piece, each fed data through props from its parent:

Home (page.js) — owns the tasks array
AddTaskForm
owns its own input text; calls onAddTask(text)
TaskList
loops tasks → renders one TaskItem per task
TaskItem × N
renders one row; calls onToggle / onDelete

Notice where state actually lives: only in Home. Everything below it is handed data and functions through props — a child never owns the real data, it just gets access to read it and ask the parent to change it.

02 Data flow — click to pixel, the React way

Compare this to Project 2's pipeline (action → handler → array change → manual save → manual re-render). React collapses the last step entirely:

1 · ActionUser clicks Add / checkbox / DeleteInside a child component
→
2 · Prop callChild calls onAddTask / onToggle / onDeleteA function handed down from Home
→
3 · setTasksHome builds a NEW arrayspread / map / filter — never mutate
→
4 · ReactAutomatic re-renderNo render() call anywhere
→
5 · useEffectSaved to localStorageFires because tasks changed

Step 4 is the whole point of React: you never write the code that updates the screen. You only ever change the data (via setTasks), and React figures out what to redraw.

03 Three builds, three philosophies

Project 1 — static
  • Content fixed in HTML
  • JS only toggles a CSS class
  • No data, no build step
Project 2 — vanilla JS
  • Data drives the screen
  • YOU write the redraw logic
  • Manual event delegation
Project 3 — React
  • Data drives the screen
  • REACT writes the redraw logic
  • Props replace manual data-* wiring

04 Key aspects this project covered

RE·01

Components

Small, reusable functions that each return a piece of the UI.

RE·02

JSX

HTML-like syntax inside JS; className instead of class; {} for live values.

RE·03

Props

How data and functions flow down from parent to child components.

RE·04

useState

React-managed data; changing it via its setter auto-triggers a re-render.

RE·05

Immutability

Always build a new array/object (spread, map, filter) — never mutate in place.

RE·06

useEffect

Syncing with the outside world (localStorage) after render, not during it.

05 Two bugs, two real lessons

Bug 1 — Delete button invisible

Code was correct in every file, but a stale Turbopack dev-server cache wasn't picking up the change. Fixed with a full restart (Ctrl+C, then npm run dev again). Lesson: when saved code doesn't seem to reflect in the browser and there's no console error, suspect the dev server's cache before suspecting your code.

Bug 2 — Vercel build failed: Module not found

The components folder was locally named Components (capital C). Windows' filesystem doesn't distinguish that from components, so it worked fine locally — but Vercel builds on Linux, which treats them as two different folders entirely. Lesson: "it works on my machine" isn't proof it'll work once deployed to a different operating system — casing is one of the most common ways this bites people.

06 Deployment — the first real build step

Projects 1–2 had Vercel serve files exactly as committed — zero build step. Project 3 is different: Vercel runs npm run build on every push, which compiles JSX into plain JS and bundles everything for production, before serving it. Deployed as a third, independent Vercel project on the same combined repo — Root Directory scoped to project-3-todo-react, exactly like Projects 1–2's pattern, just with a real compile step in between push and live site.
