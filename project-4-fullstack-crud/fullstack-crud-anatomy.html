Overview

Projects 1–3 all ran entirely inside one browser tab. Project 4 is the first app made of three separate programs, each deployed independently, that only work together because they're explicitly configured to trust and find each other. That's the entire shift this project teaches: not new UI skills, but what it actually takes to make an app's data real, permanent, and shared.

The task list itself is intentionally the same simple concept as Projects 2 and 3 — the point was never the to-do list. It was building, debugging, and deploying a genuine three-tier system, the same shape almost every real product (a bank app, an email client, a course platform) is built on.

Three-tier architecture

Tier 1 — what you see Next.js frontend deployed on Vercel
→fetch()
Tier 2 — the trusted middleman FastAPI backend deployed on Render
→SQLAlchemy
Tier 3 — permanent storage Postgres database hosted on Neon

The middle tier exists for one reason: browser code is visible to anyone (view-source, dev tools), so it can never be trusted with database credentials. FastAPI is the only piece allowed to hold the real connection string and talk to Postgres directly — the frontend only ever talks to FastAPI's public API.

Key concepts

CRUD

Create / Read / Update / Delete

Mapped onto POST, GET, PUT, DELETE — the four operations nearly every app's data layer needs.

ORM

SQLAlchemy models

Python classes (Task) that describe a database table's shape, instead of writing raw SQL by hand.

Validation

Pydantic schemas

TaskCreate / TaskUpdate / TaskOut define what a request must contain and what a response looks like — separate from the database shape.

Security

CORS

The backend explicitly allow-lists which frontend origins may call it — without it, browsers block the request by default.

Config

Environment variables

DATABASE_URL and NEXT_PUBLIC_API_URL keep secrets and per-environment settings out of the code itself.

State

Database as source of truth

Unlike Project 3's array, React's tasks state here is just a cache — Postgres is what's actually real.

Bugs, debugged for real

Every one of these was an actual failure hit mid-build, not a scripted lesson — which is exactly why they're worth keeping.

Invisible connection string

Out-File -Encoding utf8 in PowerShell silently added a byte-order-mark to .env, which python-dotenv couldn't parse past — DATABASE_URL came back as None. Fixed by editing the file directly in a text editor instead of via that command.

Malformed connection string

Once the BOM issue was fixed, the next error was more specific: wrong scheme prefix and a missing @ separator. Re-copying the connection string fresh from Neon's dashboard (rather than hand-editing it) resolved it.

Render's default Start Command

Render pre-fills gunicorn your_application.wsgi — a Django convention. Caught before the first deploy and replaced with uvicorn main:app --host 0.0.0.0 --port $PORT.

CORS blocked the live frontend

The deployed page loaded but stuck on "Loading tasks..." forever — the backend's CORS allow-list only had localhost:3000. Diagnosed via the browser console's exact error text, fixed by adding the real Vercel URL to allow_origins.

Deployment — two services, not one

Projects 1 and 3 each deployed a single Vercel project. This project deploys two independent services to two different hosts, and each needs its own Root Directory scoping since both live inside the same combined repo.

PieceHostRoot DirectoryKey setting
BackendRenderproject-4-fullstack-crud/backendStart Command + DATABASE_URL env var
FrontendVercelproject-4-fullstack-crud/frontendNEXT_PUBLIC_API_URL env var

Render's free tier also spins an idle backend down after inactivity — the first request afterward can take up to ~50 seconds to wake it. Not a bug, just the tradeoff of the free tier.
