# Project 4: Full-Stack CRUD App — Chat Log
Started 2026-08-29

## Kickoff
Explained what Project 4 is: a full-stack CRUD (Create/Read/Update/Delete) app, the first
project where data is stored permanently in a real database instead of the browser's
localStorage (Projects 2-3). Walked through why 3 separate pieces are needed and how they
talk to each other:
- Next.js frontend — the browser UI (same skills as Project 3)
- FastAPI backend — a Python program that sits between frontend and database; the ONLY
  piece allowed to talk to the database directly (frontend code is visible to anyone via
  browser dev tools, so it must never hold database credentials)
- Postgres database — permanent storage on a real server, organized as tables

Full request flow explained: user action in Next.js -> fetch request to FastAPI -> FastAPI
validates and talks to Postgres -> Postgres confirms -> FastAPI responds -> Next.js updates
the screen.

## Database host decision: Neon vs Supabase
Explained both are Postgres hosting providers (neither invented Postgres, they just run it
for you). Recommended Neon over Supabase since Neon is a focused pure-Postgres host with a
simple free tier and one connection string, while Supabase bundles auth/storage/realtime
features that would tempt shortcuts around writing FastAPI's CRUD logic by hand -- exactly
the skill this project exists to teach. Supabase's auth features will be introduced properly
in Project 5 instead.

## Bug: DATABASE_URL not loading
First attempt to create .gitignore/.env via PowerShell heredoc-style commands failed --
the multi-line content got typed as literal terminal commands instead of file content
("term not recognized" errors). Fixed with proper PowerShell Out-File syntax.
Second bug: after wiring up database.py (SQLAlchemy engine + session) and running the
server, got `sqlalchemy.exc.ArgumentError: Expected string or URL object, got None` --
DATABASE_URL was not being read at all. Root cause: `Out-File -Encoding utf8` in
PowerShell writes a UTF-8 byte-order-mark (BOM) at the start of the file, which
python-dotenv doesn't strip, so it failed to recognize the DATABASE_URL line entirely.
Fixed by editing .env directly in VS Code's text editor instead (bypassing PowerShell's
file-writing quirk).
Third bug (after that fix): error changed to `Could not parse SQLAlchemy URL from given
URL string` -- the pasted connection string had a wrong scheme prefix (`neon-postgresql://`
instead of `postgresql://`) and was missing the `@` separating the password from the
hostname. Fixed by re-copying the connection string fresh from Neon's dashboard "Connection
string" field (not typed/edited by hand) and pasting it in cleanly. Server started with no
errors after this.

## Database model + table creation
Created models.py defining a SQLAlchemy `Task` model (id primary key, text, done boolean
default False) mapping to a `tasks` table. Updated main.py to call
`Base.metadata.create_all(bind=engine)` on startup, which created the real `tasks` table
inside the Neon database automatically -- verified visually in Neon's Tables view (id
serial, text varchar, done boolean, 0 rows).

## CRUD API endpoints
Created schemas.py (Pydantic models: TaskCreate, TaskUpdate, TaskOut) -- explained the
models.py (database shape) vs schemas.py (API request/response shape) distinction.
Wrote main.py's four CRUD endpoints: GET /tasks, POST /tasks, PUT /tasks/{task_id},
DELETE /tasks/{task_id}, plus a `get_db()` dependency that opens/closes one database
session per request. Explained PUT's "only update fields that were actually sent" pattern
using TaskUpdate's optional fields.

## Testing via Swagger UI (/docs)
Verified all 4 endpoints live against the real Neon database using FastAPI's
auto-generated interactive docs at http://127.0.0.1:8000/docs:
- POST /tasks: created two rows (ids 1 and 2), confirmed live in Neon's table view.
- GET /tasks: confirmed both rows returned.
- PUT /tasks/1: set done=true. Note/lesson: text also got overwritten to the literal
  word "string" because Swagger's "Try it out" pre-fills BOTH fields as placeholders, and
  the leftover `"text": "string"` in the body wasn't deleted before clicking Execute --
  this was NOT a bug, it was TaskUpdate's "if a field is included, update it" logic
  working exactly as written. Lesson: to leave a field untouched, delete it from the
  request body entirely, don't just leave the placeholder value.
- DELETE /tasks/2: removed it. Final state confirmed in Neon: 1 row remaining (id 1,
  text "string", done TRUE). Full CRUD cycle proven working end-to-end.

## CORS
Added FastAPI's CORSMiddleware to main.py, allowing requests specifically from
http://localhost:3000 (where Next.js's dev server runs) -- explained browsers block
cross-origin requests by default unless the backend explicitly allows them, and this
would otherwise silently break every frontend fetch call once built.

## Frontend-backend connection code
Created lib/api.js -- four functions (getTasks, createTask, updateTask, deleteTask) that
wrap fetch() calls to the FastAPI backend at http://127.0.0.1:8000, matching the four
endpoints already tested via Swagger.
Recreated the three UI components from Project 3 (TaskItem.js, TaskList.js,
AddTaskForm.js) -- functionally identical, this time named `components` (lowercase) from
the start to avoid Project 3's case-sensitivity bug. One real change: TaskItem/TaskList
now key off `task.id` (a permanent, database-assigned number) instead of array index,
since index was only safe to use with Project 3's local-only array.
Rewrote app/page.js to fetch initial tasks from the backend on mount (a single useEffect,
vs. Project 3's two -- explained why: localStorage needed an explicit save step since
nothing happens automatically when you write to it, whereas here each handler calls the
backend directly, so the database updates immediately and there's nothing left to
separately "save"). Added a `loading` state shown while the initial fetch is in flight.
Each handler (add/toggle/delete) now awaits the real network call first, then updates
local React state to match.
