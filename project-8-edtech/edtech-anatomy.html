Project 8 of 10 · Anatomy

Mini EdTech Platform

A rehearsal for Project 9's flagship education platform: an admin role that creates courses, lessons, and multiple-choice quizzes through a real UI (not database seeding), and a student role that enrolls, works through lessons, tracks progress, and takes quizzes with unlimited retakes.

Next.js PWA→ FastAPI + JWT + role check→ Postgres · Vercel+Render+Neon

Overview

Every prior project in this track had exactly one kind of user. Project 8's job was to introduce a second kind — an admin role with real authoring power over content — without that becoming a security hole a student could route around. The scope: admin creates courses and lessons (text plus embedded video) and multiple-choice quizzes; students browse, enroll, mark lessons complete, see a per-course progress bar, and take quizzes with full attempt history. The first admin account itself has no self-service signup path — it's promoted by hand with a direct SQL update, which is the normal way to bootstrap the first privileged account in a system like this.

What made this project genuinely different from a CRUD app with two roles bolted on was that almost every feature had a second, invisible requirement sitting underneath it: progress only means something once enrollment exists to gate it, and a quiz endpoint only works correctly once it's actively hiding information from exactly one of its two audiences.

Roles & access control

A single role column on User ("student" or "admin") backs everything. require_admin() is a FastAPI dependency chained directly off the existing get_current_user() — it reuses the JWT-decoding logic from every prior project and simply adds one check: if current_user.role != "admin", raise a 403 before the route body ever runs. Every course/lesson/quiz create, update, and delete endpoint depends on require_admin(); every browsing, enrollment, and quiz-taking endpoint depends on the plain get_current_user(). The frontend also redirects by role after login (admin → /admin, student → /student), but that redirect is a convenience, not the actual security boundary — the backend dependency is.

Quiz grading & answer-hiding

One Quiz/Question/Option model backs both roles. Two separate Pydantic response schemas control what actually leaves the server for each: QuizOut (student-facing — questions and options, no is_correct anywhere in the payload) and QuizAdminOut (admin-facing — everything, including which option is correct, needed so the edit page can prefill the current answers). GET /quizzes/{id} always returns QuizOut; the separate admin-only GET /admin/quizzes/{id} is the only route that ever returns QuizAdminOut, and it sits behind require_admin(). Submitting an attempt (POST /quizzes/{id}/submit) takes the student's chosen option IDs, looks up the real is_correct values server-side, computes the score, and only then writes a QuizAttempt row — the client never calculates or can influence its own score.

API design

Hiding data is a schema problem

QuizOut vs. QuizAdminOut control what leaves the server — not what the frontend chooses to render.

ORM

A missing relationship fails silently

No crash when Course↔Quiz was absent — just a feature that couldn't be built later.

Authorization

Enrollment as a real gate

Not just a record — the actual check POST /lessons/{id}/complete makes before writing anything.

Reliability

Idempotent writes

Re-marking a lesson complete is safe to repeat — it doesn't double-count progress.

PWA

Service worker scope is per-origin

An old project's service worker on the same port can silently hijack a brand-new one.

Bugs, debugged for real

Every one of these was an actual failure hit mid-build, not a scripted lesson.

Missing Course↔Quiz relationship

Never added when Quiz was first modeled alongside Course/Lesson. Nothing crashed — course.quizzes just wasn't accessible, and deleting a course left its quizzes orphaned instead of cascading. Fixed with a proper two-sided back_populates relationship once the quiz-builder UI needed to list a course's quizzes.

Leftover service worker from Projects 5/6/7 hijacking localhost:3000

Made a brand-new Project 8 admin page render as plain unstyled text and login silently do nothing — a service worker's scope is the browser origin, not any one project. Confirmed via DevTools Network tab showing (ServiceWorker) as the Initiator for every single request. Fixed via Application → Service Workers → Unregister, then Application → Storage → Clear site data, then a fresh tab.

Relative import path-depth miscount

app/admin/courses/[id]/quizzes/new/page.js used 5 ../ to reach lib/api.js but needed 6 — one folder deeper than the sibling quiz-edit page, which got its own path count right. Caused a real "Module not found" Turbopack build error live during testing. Fixed, then verified by resolving the path against the actual file on disk.

git push failing from the device-bridge sandbox

Expected, not a real bug: the sandbox has no stored GitHub credentials by design. The final commit had to be pushed from the user's own Terminal, where real credentials live — same as every prior deploy in this track.

Render's "Add from .env" paste not parsing correctly

Pasting the full .env file content dropped the entire DATABASE_URL=postgresql://... line into the KEY field as one string instead of splitting it into key and value. Worked around by adding DATABASE_URL and SECRET_KEY as two separate, manually-typed rows instead.

CORS blocking the real deployed frontend

Backend's allow_origins only listed localhost:3000 and "null". The live Vercel app failed every request with "Failed to fetch" — not a broken backend, just a backend correctly rejecting a browser origin it didn't recognize. Fixed by adding the exact deployed Vercel URL to allow_origins.

Render not auto-redeploying immediately after the CORS-fix push

Same class of issue hit in Project 7: a push reaching GitHub doesn't guarantee an immediate redeploy. Resolved with a manual "Deploy latest commit" from the Render dashboard; worth checking the Auto-Deploy setting going forward.
